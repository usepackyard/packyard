# Internationalization (i18n)

Packyard's dashboard supports multiple languages. The backend is English-only (logs, Composer protocol, external API consumers); user-visible strings live in the frontend. Backend error responses emit stable snake_case **codes** that the frontend translates via the `errors` catalog.

Status: **English** and **Macedonian (mk)** ship translated. Login, Profile, Dashboard, Packages, Tokens, Users, Members, and all super-admin screens route through `t()`. Error codes, pluralization, and locale-aware date/number formatting are wired end-to-end.

## Architecture

**Library**: [`react-i18next`](https://react.i18next.com/). JSON catalogs in `frontend/src/locales/<lang>/<ns>.json`.

**Namespaces** (one file per screen area):
- `common` — app shell, buttons, generic words (`save`, `cancel`, `loading`)
- `auth` — login page
- `profile` — user profile page
- `errors` — maps backend error codes to user-visible messages (populated in Phase 3)

**Language priority** (highest wins):
1. `user.language` — the logged-in user's preference, stored in `users.language` (DB column), surfaced by `GET /api/auth/me`, applied via `applyUserLanguage()` in `frontend/src/i18n/index.ts`.
2. `localStorage("packyard:lang")` — set by the pre-login picker on `Login.tsx`. Also mirrors the DB value after login so cold-starts render in the right language before `/api/auth/me` returns.
3. `"en"` — fallback. **English is always the default for a new user.** There is no `navigator.language` sniffing; we don't want to auto-pick a locale we can't fully support.

**Supported locales** (single source of truth in two places that must stay in sync):
- Backend: `supportedLanguages` map in `internal/handler/admin_auth.go`.
- Frontend: `SUPPORTED_LANGUAGES` in `frontend/src/i18n/index.ts`.

Adding a locale is a deliberate two-line change: add the code to both lists, plus a matching JSON catalog directory. Drift between the two would either hide a catalog (frontend has it, backend rejects the PUT) or accept an invalid value (backend stores `"fr"`, frontend renders English fallback forever).

## How to add a new string

1. Pick a namespace based on where the string lives (screen area).
2. Choose a key by UI location, **not** English text — keys should survive rewording:
   - Good: `packages.delete.confirmTitle`
   - Bad: `packages.areYouSureYouWantToDelete` (English-shaped; rewording breaks translations)
3. Add it to `frontend/src/locales/en/<ns>.json`.
4. Add it to `frontend/src/locales/mk/<ns>.json` (copy the English value if you don't speak Macedonian — missing keys fall back to `en` at runtime, but we prefer explicit parity so the canary locale catches drift).
5. Use it:
   ```tsx
   import { useTranslation } from "react-i18next";
   const { t } = useTranslation("packages");
   return <h2>{t("delete.confirmTitle")}</h2>;
   ```
   Or cross-namespace: `t("packages:delete.confirmTitle")`.

TypeScript types are auto-derived from the English catalogs (see `frontend/src/i18n/keys.d.ts`), so `t("typo.here")` fails the build.

## How to add a new locale

1. Add the code (e.g. `"fr"`) to `SUPPORTED_LANGUAGES` in `frontend/src/i18n/index.ts`.
2. Add the same code to `supportedLanguages` in `internal/handler/admin_auth.go`.
3. Create `frontend/src/locales/fr/` with the four namespace files (start by copying `en/` so missing keys are explicit).
4. Import them in `frontend/src/i18n/index.ts` and register under `resources.fr`.
5. Add a display label for the locale to `frontend/src/locales/*/profile.json` under `language.<code>` (each locale names *all* locales in that locale's alphabet — e.g. French spells "Macedonian" as "Macédonien").

## How to add a new namespace

1. Create `frontend/src/locales/{en,mk,...}/<ns>.json`.
2. Import in `frontend/src/i18n/index.ts`, add to the `ns` array and to `resources.<lang>.<ns>`.
3. Add to `CustomTypeOptions.resources` in `frontend/src/i18n/keys.d.ts` so `t()` types update.

## Dates, numbers, relative time

Always pass the active `i18n.language` to `Intl.*` formatters:
```ts
new Intl.DateTimeFormat(i18n.language, { dateStyle: "medium" }).format(date);
```
Inline `.toLocaleDateString()` without a locale argument uses the browser default, which may disagree with the user's chosen language. Phase 2/4 sweeps through every such call.

## Backend error codes

`writeError(w, status, code, message)` — the `code` is a stable snake_case identifier, the `message` is the English fallback. The envelope is:

```json
{"code": "invalid_payload", "message": "Invalid payload", "error": "Invalid payload"}
```

(The `error` field is a legacy alias for `message`, kept for external integrations during the transition.)

Frontend `api/client.ts` throws `ApiError` with a translated message resolved via `i18n.t("errors:" + code)`, falling back to the server's English `message`, then to the catalog's `generic`. This means codes not yet in the catalog still surface reasonable text instead of a blank alert.

**Adding a new error code:**
1. `writeError(w, http.StatusBadRequest, "my_new_code", "My new code prose.")` in your handler.
2. Add `"my_new_code": "My new code prose."` to `frontend/src/locales/en/errors.json`.
3. Add the same key (translated) to `frontend/src/locales/mk/errors.json` and every other locale.
4. `go test ./internal/handler/ -run TestErrorCodeRegistry` — asserts every used code has a catalog entry and every catalog entry has a call site (dead keys fail the test, except the `generic` frontend-only fallback).

Out of scope: Composer protocol endpoints (`/packages.json`, `/p2/*`, `/dist/*`) and structured logs — both stay English.

## Pluralization

Use i18next's `_one` / `_other` suffix convention for count-dependent strings:

```json
{
  "packages.count_one": "{{count}} package",
  "packages.count_other": "{{count}} packages"
}
```

```tsx
t("packages.count", { count: n })  // picks _one or _other based on n
```

Multi-count strings (e.g. "3 owners · 5 members") should compose two translated sub-strings rather than use multiple placeholders with English-shaped `{{ownersS}}` flags. See `dashboard.stats.owners` / `dashboard.stats.membersCount` for the pattern.

## CI guards

Two tests block merges on i18n drift — both run as part of `go test ./...`:

1. **`TestErrorCodeRegistry`** (`internal/handler/errors_registry_test.go`): AST-walks `writeError(...)` call sites, asserts every code exists in `en/errors.json` and no catalog entry is dead.

2. **`TestLocaleParity`** (`internal/handler/locale_parity_test.go`): Every non-English locale must have every key that exists in `en/*.json` (across all namespaces). Extra keys in non-English locales are allowed; missing keys fail. New locales are auto-discovered by directory listing — no test update needed when adding one.

The English catalog is always the source of truth. Non-English locales are allowed to lag on new keys (i18next falls back to en at runtime), but must close the gap before merge.

## Contributor guide

**Translating to a new locale (e.g. `de`):**
1. Add `"de"` to `SUPPORTED_LANGUAGES` in `frontend/src/i18n/index.ts`.
2. Add `"de": true` to `supportedLanguages` in `internal/handler/admin_auth.go`.
3. `mkdir frontend/src/locales/de && cp frontend/src/locales/en/*.json frontend/src/locales/de/` — start from English placeholders.
4. Translate each file. Keep the keys identical; translate only the values.
5. Add a display label for the locale to every `profile.json` under `language.de` (each locale names all locales in its own alphabet — English spells "German", German spells "Deutsch", Macedonian spells "Германски").
6. Import the catalog JSONs in `frontend/src/i18n/index.ts` and register under `resources.de`.
7. `go test ./internal/handler/ -run TestLocaleParity` — will complain if any key is missing.
8. `cd frontend && bunx tsc -b` — will complain if any new TypeScript-typed key is misspelled.

**Translating a single string:**
1. Edit the relevant `frontend/src/locales/<lang>/<ns>.json`. Don't add new keys — coordinate with whoever's changing the English source, because missing-key drift is a merge-blocker.
2. `make frontend` to rebuild; open the dashboard and switch to your locale via **Profile → Preferences → Language** to see the change.

**Reporting a bad translation:** open an issue with the key path (`packages:detail.source.configTitle`) and the locale. Avoid including screenshots of the bad string alone — the key path is what a translator needs.

## Operational notes

- **Migration safety**: the `users.language` column was added idempotently in `internal/database/migrations/001_initial.go` — fresh installs get it via `CreateTable`, existing installs get it via a try-and-ignore `ALTER TABLE`. Default is `'en'` so existing users keep working without intervention.
- **CSRF**: `PUT /api/auth/me` requires `X-Requested-With: XMLHttpRequest` (same as other mutating endpoints).
- **Session scope**: language changes affect the logged-in user only — no shared-tenant state, no org-level default.
